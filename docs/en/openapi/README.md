# OpenAPI import and source editing

[Русский](../../ru/openapi/README.md)

The `openapi` module accepts document bytes and interprets YAML or JSON as OpenAPI. It depends on `core`; loading files, fetching URLs and saving documents belong to the caller. The source is retained independently of the partial semantic model, so unsupported document sections are not discarded on import.

## Import

Call `OpenApiImporter.importDocument(bytes, options)`, using `ImportOptions.autoDetect()` or an explicit `withFormat(...)` hint. The importer retains the original bytes, checks UTF-8 and syntax, detects duplicate keys, and accepts OpenAPI 3.0.x and 3.1.x. Scalar inputs can require an explicit format. `ImportResult` exposes the status, diagnostics, detected format and version when available, and an optional document. `IMPORTED` means a model was produced; parser diagnostics can still be present and do not imply full OpenAPI validation. An unsuccessful import retains the source but has no editable model. Returned source bytes and model snapshots are defensive copies.

The current mapping covers selected `info` fields and schema components, including supported nested schema fields and values. It does not yet map paths, operations or all other OpenAPI objects. Source preservation does not mean these sections are represented in `core` or validated completely. External references are not resolved or fetched. Some inputs, including schemas the underlying parser fails to interpret, are rejected with a mapping diagnostic.

Schema `default`, `example`, `examples`, `enum` and `const` values retain the decimal precision of JSON and YAML numbers, including numbers nested in arrays and objects. The six integer constraints `minProperties`, `maxProperties`, `minItems`, `maxItems`, `minLength` and `maxLength` are read from the source as `BigInteger`, so values above `Integer.MAX_VALUE` are retained in the model after import and editing. This does not add validation of negative or non-integer constraint values; the underlying parser's existing handling still applies to values that are not decimal integers.

## Editing

`OpenApiSchemaEditor` supports schema component rename/add/delete, property add/rename/delete, and schema-object update. Commands use the identifiers from the imported model. The editor applies the semantic command to a copy, patches the source and imports the result again. Before returning success, it compares the schema components in the semantic result with the schema components from that re-import, including nested properties, values and references while ignoring generated `ElementId` values. Only schema component data currently represented in `core` is compared; source sections not yet mapped, such as paths, remain outside this check. A mismatch throws `IllegalArgumentException` and no successful result is published. A successful result carries the new source and an `ImportResult` state whose model preserves the semantic result's identifiers; pass that state to the next operation. An unchanged rename or update preserves the original source bytes. Semantic rejection returns the original state and no source in the edit result. Deletion checks references in the semantic model and in source sections not yet mapped to `core`, such as paths. Invalid editor input, unsupported source changes, ambiguous YAML and failed source verification can instead throw `IllegalArgumentException`; no partial result is published. See [core editing](../core/editing.md) for command and change semantics.

Updates and structural edits patch only the selected source nodes rather than serializing the complete document. Property rename also updates matching `required` names and local pointers to that property subtree. The renamed entry keeps its position in `required`. If `required` already contains the new property name, the old entry is removed from the source array and the order of the remaining entries is preserved. When an update changes `required`, only the added or removed array items are edited: removed items are deleted in place and added items are appended with the separator and indentation of the existing array, so the rest of the array is not rewritten. A reorder alone leaves the source untouched. The edit is refused when the array is shared through a YAML alias, contains a non-string item, or has a comment next to a removed item.

The order of `required` is kept as written in the source on import, and the model comparison after an edit treats `required` as a set: the order of names is not significant for the result check, but the source order is preserved. Reference relocation uses the OpenAPI object structure, including sections not yet mapped to `core`. Literal values and extension payloads are preserved. See the reference-location rules below. A discriminator mapping key named `$ref` is treated as a mapping label, not as a reference field. Delete commands reject incoming references outside the deleted subtree and preserve empty `properties` or `schemas` sections as `{}`. To avoid discarding unknown fields or comments, an update cannot replace or remove an existing `properties`, `items`, `additionalProperties`, `allOf`, `oneOf`, `anyOf`, `not` or `discriminator` value through its parent. Target an existing nested schema directly for its field updates, or use `addProperty` to add a property. Adding a previously absent nested field is supported when representable in the selected OpenAPI version. Literal values explicitly replaced by a command are replaced as a whole.

For OpenAPI 3.1, schema component or property renames and deletions return `EditCode.INVALID_STRUCTURE` when a non-literal `$id` key is found outside literal values and extension payloads. `$id` changes the base URI for relative references, while the current editor does not resolve references in those URI scopes. Because some Schema Object locations are not yet mapped, the guard conservatively rejects the whole structural edit, including references outside the `$id` subtree, and returns the original state without source. A `$anchor` alone does not change the base URI and does not trigger this refusal. OpenAPI 3.0 documents are not subject to this guard.

YAML aliases, merge keys, comments and flow mappings can make an edit ambiguous; affected operations may reject such input rather than modify it. In particular, deletion refuses ambiguous leading or trailing comments and comments between a removed block entry and its sibling; comments inside a deleted node are removed with that node. The supported source edits are narrower than the set of valid OpenAPI documents, and import is not a promise that every subsequent edit can be applied.

Before a YAML schema or property addition, `updateSchema`, or schema/property deletion, the editor detects nodes shared through aliases along the mutation path and within a replaced or removed value. It rejects those edits with `IllegalArgumentException` so an edit cannot silently change another schema or leave the imported model inconsistent. Aliases elsewhere in the document do not by themselves prevent an edit.

Removing the sole entry of a block mapping keeps the following key, its indentation and intervening blank lines. Replacing a literal (`|`) or folded (`>`) scalar, or an empty scalar such as `default:`, keeps the next key on its own line and inserts the space required after `:`. An inline comment on the block scalar indicator or empty scalar causes a safe refusal because its ownership is ambiguous. Adding a field after a multiline flow array or mapping places it after the closing `]` or `}` and preserves nearby comments and line endings.

## Reference locations in schema edits

Schema component and property rename/delete share the same source reference classification. It follows object roles recursively rather than matching paths of a fixed depth:

- Schema Objects in `components.schemas`, parameter/header `schema`, and Media Type `schema`; nested schema maps (`properties`, `patternProperties`, `dependentSchemas`, `$defs`, `definitions`), single-schema keywords (including `items`, `additionalProperties`, `contains`, `if`/`then`/`else`, `unevaluatedItems`, `unevaluatedProperties`, `contentSchema`) and schema arrays (`allOf`, `anyOf`, `oneOf`, `prefixItems`). Discriminator mapping values are also relocated.
- Path Items in `paths`, OAS 3.1 `webhooks` and `components.pathItems`, and callback expressions under operation callbacks or `components.callbacks`. Callback nesting can repeat at any depth. Path/operation parameters, operation request bodies and responses use the same rules in every Path Item.
- Media Types in request-body/response content and parameter/header content. Encoding headers recurse through the same Header and Media Type roles, including nested `encoding.*.headers`.
- Reference Objects in reusable parameters, headers, request bodies, responses, callbacks, examples, links, security schemes and path items; inline parameter, header, request-body, response, callback, example and link positions; and the Path Item `$ref` field. This classification locates reference fields; it does not validate that their target has the required OpenAPI object type.

Every source `$ref` is classified as recognized, opaque (literal or extension payload), or unrecognized. Schema literal keywords, parameter/media examples, Example Object `value`, Link Object parameter/request-body values and `x-*` payloads are opaque. Named map entries such as a property or header named `x-name` or `example`, and discriminator mapping labels including `$ref`, remain names rather than literal/extension fields. Extensions of the `paths` object are opaque too.

A recognized local pointer to a renamed component/property or its descendants is relocated. An unrecognized `$ref` targeting that subtree refuses rename with `IllegalArgumentException` listing all unrecognized locations. Delete returns `EditRejected(REFERENCED_TARGET)` listing all incoming recognized and unrecognized locations outside the removed subtree, including locations absent from the semantic model. Unrelated, external and opaque values remain unchanged. Refusal leaves the input model and original bytes unchanged; no partial edit is published. These rules do not add external-reference resolution or remove the existing OAS 3.1 `$id` scope restriction.

The versioned YAML/JSON catalogues `reference-locations-3.0.*` and `reference-locations-3.1.*` in the module test resources, with their location manifests and expected renamed documents, provide a reusable inventory of these reference roles.
